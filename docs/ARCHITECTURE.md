# Architecture Technique - LMU-DeltaRacing

## Couches du projet
- `Domain` : Entités métier immuables (`Session`, `Driver`, `Lap`, `Sector`) sans dépendance externe. `Session.Kind` (essais, qualification, course) et `Driver.BestLap` (meilleur tour chronométré) sont calculés une fois à la création : les vues les lisent au lieu de comparer le nom de la phase ou de parcourir les tours.
- `Application` : Contrats du parser XML, du dépôt de sessions, des services d'import, contrats de métriques et traces.
- `Infrastructure` : parser XML LMU en flux (`XmlReader` : le journal d'événements `Stream` est sauté sans être chargé), dépôt en mémoire et watcher du dossier de résultats avec traitement séquentiel, retries sur les fichiers verrouillés et déduplication par chemin.
- `Console` : application console Spectre.Console (Accueil, Mes courses, Options) sur les services partagés de `Presentation`, export OpenTelemetry et statistiques d'exécution.
- `Presentation` : code partagé par l'UI et la console : calculs des vues (`*Presentation`), service de données (`DashboardDataService` : import initial, rechargement, watcher, fusions de pilotes, détection du pilote principal), écriture des réglages (`DashboardSettingsStore`) et détection du dossier de résultats (`ResultsDirectoryResolver`).
- `UI` : Dashboard Blazor interactif local : composants Razor alimentés par `Presentation` (les pages dérivent de `DashboardPage`, qui suit l'état du service, et affichent chargement et erreur via `ResultsGate`), sélecteur de dossier Windows et géométrie du graphique SVG de Progression.
- `Tests` : tests unitaires et d'intégration MSTest + FluentAssertions ; les benchmarks sont dans le projet MSTest `benchmarks/LMU-DeltaRacing.Benchmarks`.

## Flux de données
1. Le parser consomme un `Stream` XML LMU via la couche `Application` pour garantir l'indépendance du système de fichiers.
2. Le parser transforme le XML en entité `Domain.Session`.
3. Le dépôt en mémoire enregistre et restitue les sessions de manière thread-safe.
4. Au chargement, `DashboardDataService` analyse les fichiers en parallèle (un cœur reste libre pour l'affichage) mais prend leurs résultats dans l'ordre des fichiers, un à la fois : progression, échecs et `StateChanged` sont rapportés comme par un import séquentiel. Les fusions de pilotes et les fréquences sont calculées une fois, en fin de chargement.
5. Un fichier qui n'est pas un résultat LMU, ou toute erreur inattendue pendant l'import d'un fichier, est compté en échec : ni le chargement ni la surveillance ne s'arrêtent.

## Monitoring, Logging & OpenTelemetry

L'application utilise **OpenTelemetry** couplé au système de logging standard de .NET :
- **Format des logs :** Les journaux écrits dans `lmu-deltaracing.log` utilisent JSON Lines : un objet JSON structuré par ligne, sans tableau JSON englobant.
- **Fichier courant :** Les logs sont écrits dans `lmu-deltaracing.log`, à côté de l'exécutable. À l'arrêt, le fichier est fermé mais conservé pour consultation. Il est écrasé au démarrage suivant afin de ne conserver que l'exécution courante.
- **Statistiques :** `lmu-deltaracing-stats.json` contient le résumé OpenTelemetry de la dernière exécution : durée moyenne d'import, débit en fichiers par seconde, mémoire moyenne du processus (working set et heap .NET), nombre de fichiers et résultats d'import. Le fichier est fermé et conservé à l'arrêt, puis remplacé au prochain démarrage.
- **Traces et métriques :** Elles sont exportées vers la sortie Debug, et non vers le terminal. L'instrumentation runtime publie également des métriques du processus.
- **Masquage des données sensibles :** Seul le nom du fichier XML, et non son chemin local absolu, est consigné dans les traces.

## Stratégie de Performance & Tests de Charge

Pour garantir la fluidité sur de gros volumes d'historiques (par exemple des centaines de fichiers XML de course) :
- Une suite MSTest dédiée (`benchmarks/LMU-DeltaRacing.Benchmarks`) mesure le parser, la chaîne d'import et les calculs de chaque page (voir [Benchmarks](#benchmarks)).
- Un rapport de performance (`benchmarks/LMU-DeltaRacing.Benchmarks/artifacts/performance-report.md`) est joint aux Pull Requests qui modifient le moteur d'import ou le parser.
- Un test verrouille le parsing des 342 fixtures par une empreinte SHA-256 de toutes les valeurs lues : une optimisation du parser ne peut pas changer silencieusement les données.
- [Audit d'octobre 2026](benchmarks/audit-performance-2026-10.md) : comparaison avant/après du parser en flux et de l'import parallèle.

## Build

`Directory.Build.props` fixe le framework cible, les usings implicites et les types nullables de tous les projets. `src/Directory.Build.props` y ajoute, pour les projets de l'application, la génération de la documentation XML (tout membre public doit être documenté) et les avertissements traités comme des erreurs, sauf les alertes d'audit NuGet. La documentation XML n'est pas publiée avec l'application.

## Configuration

La console charge `appsettings.json` depuis le dossier de l'exécutable. Comme le dashboard, elle compose `DashboardDataService` (projet `Presentation`) : la section `LMU` fournit le dossier des résultats, le pilote principal, les fusions de pilotes et le démarrage automatique de la surveillance, écrits par `DashboardSettingsStore`. Seuls les réglages du fichier de log (`LogFilePath`, `FileMinimumLogLevel`) sont liés à `LmuApplicationOptions` via `IOptionsMonitor<T>` et écrits par `LmuApplicationSettingsStore`, qui ne touche pas aux autres clés de la section. Chaque exécutable a son propre `appsettings.json`.

La console ne prend aucun argument. Au démarrage, elle importe le dossier configuré (ou détecté automatiquement par `ResultsDirectoryResolver`, comme le dashboard) avec une barre de progression, puis affiche un résumé : sessions importées, essais ignorés et échecs détaillés. Un dossier illisible n'arrête pas la console : l'erreur est affichée et le dossier se corrige dans Options. Un bandeau d'état (pilote, état de la surveillance, sessions du pilote, échecs) précède le menu principal : Accueil, Mes courses, Options, Quitter. Chaque vue efface l'écran et se termine par son propre menu. L'Accueil et Mes courses utilisent les mêmes calculs que le dashboard (`HomePresentation`, `MyRacesPresentation`, `MyRacesFilters`) et les mêmes formats (`DisplayFormat`) ; la ventilation par catégorie de l'Accueil est rendue en colonnes de tableau. Les Options reprennent les réglages du dashboard sauf les essais et le sélecteur de dossier, plus les réglages du log ; changer de dossier recharge immédiatement les résultats et la surveillance. Les sessions d'essais ne sont jamais importées. Spécification : `docs/UISpec/Console.template.md`.

Après le chargement initial, la surveillance du dossier (`FileSystemWatcher`) tourne jusqu'au choix `Quitter` si `WatchResultsOnStartup` est actif. Le service d'import ouvre exclusivement chaque fichier et effectue jusqu'à six tentatives espacées (délai maximal de 1 seconde entre tentatives) lorsqu'il est verrouillé. Il importe les fichiers XML nouveaux ou renommés et maintient un registre des chemins déjà vus en mémoire afin de neutraliser les notifications répétées. Le registre est réinitialisé à l'arrêt; au lancement suivant, le dossier est chargé à nouveau dans le dépôt en mémoire. `DashboardDataService.LiveImportCompleted` signale chaque fichier importé par le watcher : la console les met en file d'attente et les affiche au retour au menu principal, pour ne jamais écrire pendant qu'un menu est affiché. Les fichiers déjà présents au lancement sont marqués comme traités lors du démarrage du watcher pour éviter un second import.

Par défaut, `ResultsDirectory` est vide (détection automatique), `LogFilePath` est `lmu-deltaracing.log` relatif au dossier de l'exécutable et `FileMinimumLogLevel` est `Debug`. Un chemin de résultats ou de log relatif est résolu à partir du dossier de l'exécutable. Les réglages du log sont validés avant le démarrage et bloquent la console s'ils sont invalides. Aucun log n'est affiché dans le terminal ; le seuil s'applique au fichier JSON Lines.

## Dashboard Blazor

L'application Blazor compose les mêmes services de parsing, dépôt et import que la console, à une différence près : elle peut importer les sessions d'essais (option `LMU:LoadPracticeSessions`, décochée par défaut), que la page Détail des courses affiche dans un onglet dédié. Cette page regroupe les sessions en événements (essais, qualification, course) via `RaceEventPresentation`. Dans la page Options, le bouton « Appliquer » vérifie un dossier, enregistre `ResultsDirectory` dans `appsettings.json`, puis recharge les résultats et le watcher sans redémarrer ; la préférence `WatchResultsOnStartup` est enregistrée dès qu'elle est modifiée. Le sélecteur de dossier Windows natif fournit un chemin exploitable par le watcher. Les fusions de pilotes déclarées dans Options sont appliquées en mémoire aux sessions chargées, sans modifier les fichiers. Les erreurs d'import, la progression et les sessions récentes sont présentées sous le formulaire Options, sans tableau de classement des pilotes. La page d'accueil (`/`) calcule les statistiques de carrière du pilote via `HomePresentation`, sur la position en classe officielle ; le parser lit pour elle `ClassGridPos`, `DNFReason` et `TrackLength`. La page Progression (`/progression`) regroupe les meilleurs tours du pilote par période locale via `ProgressionPresentation`, puis `ProgressionChartLayout` calcule la géométrie du graphique SVG (échelles, graduations, tracés) sans bibliothèque JavaScript ; ses réglages sont enregistrés dans `LMU:Progression`. Lors d'un rechargement, le dépôt en mémoire est vidé avant l'import du nouveau dossier pour éviter de mélanger les sessions de deux sources. L'application écoute sur une adresse loopback avec un port dynamique et ouvre le navigateur par défaut. `UpdateCheckService` (hosted service) lit au démarrage le dernier tag publié via l'API GitHub, seule requête sortante de l'application, désactivable par `LMU:CheckForUpdates` : il alimente la fenêtre `UpdateNotice` (une fois par lancement) et le panneau `UpdateSettingsPanel` d'Options, dont le bouton est un simple lien vers l'installeur de la dernière release. L'application ne télécharge ni n'exécute rien elle-même, car l'installeur n'est pas signé. Les logs restent en JSON Lines dans `lmu-deltaracing.log`; le profil de publication `win-x64` est autonome et ne nécessite pas d'installation du runtime .NET.

## Benchmarks

Le projet MSTest dédié `benchmarks/LMU-DeltaRacing.Benchmarks` produit un rapport en quatre parties :
- **Parsing de XML synthétiques** : 109 500 sessions en mémoire par défaut (10 courses/jour × 3 phases × 365 jours × 10 ans), chaque session analysée étant libérée avant la suivante, puis des lots de 10 à 5 000 fichiers créés dans le répertoire temporaire et supprimés à la fin.
- **Opérations de « Mes courses »** : tri, groupement et filtres sur 1 000 à 50 000 lignes synthétiques.
- **Chaîne d'import sur les fichiers réels** (catégorie `Import`) : parsing de fichiers médians et des plus gros par type de session, import disque fichier par fichier, et chargement complet de `DashboardDataService` (sans ou avec essais, avec fusions, avec le journal JSON du dashboard), sur les 342 fixtures puis sur 5 copies.
- **Calculs des vues** (catégorie `Views`) : calculs de chaque page sur l'historique réel répété ×1, ×10 et ×50.

Chaque mesure est préchauffée ; le rapport donne la médiane, le meilleur temps et les allocations de tous les threads. Lancer `dotnet test benchmarks/LMU-DeltaRacing.Benchmarks/LMU-DeltaRacing.Benchmarks.csproj --configuration Release --filter "TestCategory=Load"` pour générer le rapport Markdown dans `benchmarks/LMU-DeltaRacing.Benchmarks/artifacts/performance-report.md`. Les filtres `TestCategory=Import` et `TestCategory=Views` affichent une partie seule dans la sortie détaillée (`--logger "console;verbosity=detailed"`), sans écrire le rapport. Si l'environnement est limité en mémoire, utiliser `-p:BenchmarkYears=5` ou `-p:BenchmarkYears=2`.

## Packaging Windows

Le profil `win-x64` publie l'UI en mode autonome et en fichier unique, sans élagage (le trimming casserait la sérialisation d'état des composants Blazor interactifs). L'unique jeu de résultats de démonstration anonymisés du dépôt est versionné dans `assets/Results` et sert aussi aux tests. `scripts/Prepare-PackageAssets.ps1` permet de régénérer ces fichiers depuis un dossier de résultats fourni par l'utilisateur; le workflow de release copie les XML versionnés vers la publication, sous `TestAssets/Results`, et n'anonymise ni ne transforme les données. Les noms des pilotes sont remplacés par des alias à prénom (`Driver Tom`, `Driver Lucas`…) cohérents sur l'ensemble du lot, y compris dans les événements du `Stream`, sans altérer les résultats LMU de l'utilisateur. Avec `-MergeSingleRaceDrivers`, les pilotes n'ayant fait qu'une course partagent l'alias d'un pilote qu'ils n'ont jamais croisé, pour des historiques de démonstration plus riches. Le workflow de release inscrit la version du tag dans l'application (`-p:Version=X.Y.Z`) ; sans cela, elle reste en `0.0.0-dev` et ne détecte aucune mise à jour. `scripts/Test-PublishedApp.ps1` vérifie l'absence de DLL externes, démarre l'exécutable, valide une réponse HTTP locale et, avec `-ExpectedVersion`, contrôle la version affichée dans Options.

`scripts/installer.iss` génère l'installeur Inno Setup. Lors d'une première installation, il cherche des XML dans les dossiers LMU courants (Documents et installation Steam) et configure `LMU:ResultsDirectory` vers le premier dossier trouvé; sinon, il utilise les fixtures anonymisées installées avec l'application. Les mises à niveau préservent le `appsettings.json` existant. Le workflow manuel `.github/workflows/release.yml` calcule la version suivante à partir du dernier tag `vX.Y.Z` et du type choisi (Majeur, Mineur, Patch), crée le tag et attache l'installeur à la release, dont les notes listent les PR fusionnées depuis la version précédente.
